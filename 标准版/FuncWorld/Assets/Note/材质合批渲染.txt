private static Material _material;
public static Material Material
{
    get
    {
        if (_material == null)
        {
            _material = new Material(UKit.shader);
            _material.enableInstancing = true; //开启GPU实例化,支持合批渲染,提高性能
        }
        return _material;
    }
} 

1. 上述Material赋值给渲染器不会产生材质副本(Material Instance)
执行spriteRenderer.material = Material时你只是将渲染器(Renderer)内部的材质指针指向了这个静态的Material
Unity中产生材质副本(即<MaterialName> (Instance))的典型操作是访问renderer.material属性(getter/setter).
通过代码直接赋值一个已存在的Material对象引用,Unity 不会自动克隆它.
使用静态属性共享同一个Material实例,能节省内存,场景中成百上千个精灵都共享同一材质而不是每个精灵都有一份独立拷贝

2. 潜在性能风险:动态合批断裂
虽然不产生内存副本,但这种写法在渲染性能上可能存在隐患,具体取决于你是否修改了该材质属性
如果只读取/赋值,不修改材质的属性‌:
所有使用该静态材质的精灵,如果纹理(Sprite Atlas)也相同,且没有其他打断合批的因素,它们‌可以‌被动态合批.这是最佳情况.

如果通过代码修改了该静态材质的属性‌:
例如:Material.color = Color.red;

全局影响‌:因为所有精灵共享同一个材质实例,修改它会‌同时改变场景中所有使用该材质的精灵的颜色‌.这通常不是预期的行为.
合批断裂‌:如果你为了区分不同精灵而尝试在每一帧或不同对象上修改这个共享材质的属性,会导致渲染状态频繁切换,严重破坏动态合批(Dynamic Batching),导致 Draw Call 激增.

如果想让每个精灵颜色不同,但又想共享材质‌:
你应该使用 ‌MaterialPropertyBlock‌ 或修改 ‌顶点颜色(Vertex Color)‌.

MaterialPropertyBlock‌:允许你在不创建材质副本的情况下,为单个精灵渲染器覆盖材质属性(如颜色、透明度).
这是Unity推荐的高效做法,既共享材质又支持个体差异,且通常不会打断合批(取决于具体属性和Shader实现,但在URP/Sprite系统中表现良好).
顶点颜色‌:在SpriteRenderer中直接修改Color属性(这是顶点颜色,不是材质颜色),这完全不会干扰材质共享,是2D游戏中最高效的变色方式.

3. 代码改进建议
方案 A:仅用于共享基础材质(推荐)

如果你的目的是让所有精灵共享同一个 Shader 和基础配置(如渲染队列、混合模式等),静态材质是很好的选择.但请确保‌不要‌在运行时通过代码修改这个静态材质的实例属性(如 _Color, _MainTex 等).

private static Material _material;
public static Material SharedMaterial
{
    get
    {
        if (_material == null)
        {
            // 确保 Shader 已正确加载
            _material = new Material(UKit.shader);
            // 可以在这里设置固定的、所有对象共有的属性
            _material.EnableKeyword("_SOME_FEATURE");
        }
        return _material;
    }
}

// 使用时:
spriteRenderer.material = MyMaterialManager.SharedMaterial; 
// 如果需要改变单个精灵颜色,请使用 spriteRenderer.color (顶点颜色) 或 MaterialPropertyBlock

方案 B:使用 MaterialPropertyBlock(针对需要动态属性的场景)

如果你需要根据逻辑动态改变每个精灵的材质属性(如闪烁、变色),请保留静态材质作为基础,但通过 PropertyBlock 应用差异:

private static MaterialPropertyBlock _mpb;

public void SetSpriteColor(SpriteRenderer renderer, Color color)
{
    if (_mpb == null) _mpb = new MaterialPropertyBlock();
    
    renderer.GetPropertyBlock(_mpb);
    _mpb.SetColor("_Color", color); // 假设 Shader 中有 _Color 属性
    renderer.SetPropertyBlock(_mpb);
}

内存方面‌:不会产生多余的材质副本,节省了内存.
渲染方面‌:只要不通过代码改这个静态材质的实例属性,它就有助于合批.如果你需要个体差异,请在渲染器上修改,如SpriteRenderer.color(顶点色)或MaterialPropertyBlock使用,切勿直接修改共享材质的属性.

/************************************************************************************************************************************************************************************/

Unity 的 renderer.material getter 具有“懒加载实例化”机制.第一次访问时,它会为每个 Renderer组件 克隆一份新的材质实例(Material Instance).
Unity 的动态合批(Dynamic Batching)或静态合批的核心前提是“多个物体使用完全相同的材质”.
对于“同材质、不同颜色/属性”的大批量物体,‌MaterialPropertyBlock‌ 是 Unity 官方推荐的标准解法.
MPB 不会创建新的材质实例,也不会修改原始共享材质.它像一个“补丁包”,存储在 Renderer 组件上.渲染时,Unity 会将 MPB 中的属性临时覆盖到共享材质上,仅对当前物体生效.

当你写 renderer.material = someMaterial 时,Unity 的行为如下:
‌Setter 行为‌:renderer.material 的 setter(赋值操作)‌不会‌触发克隆.它只是简单地将渲染器内部引用的材质指针指向 someMaterial.
‌共享状态‌:此时,renderer.sharedMaterial 也指向同一个 someMaterial.
‌结果‌:renderer.sharedMaterial == someMaterial 为 true.
‌注意设置属性只是内存赋值,不涉及资源克隆‌:只有当你‌读取‌(Getter)renderer.material时没有独立实例,才会克隆.但‌赋值‌(Setter)是直接替换引用.

在传统内置渲染管线中,使用MPB不会打断动态合批‌(只要顶点数符合限制).
在URP/HDRP中,配合GPU Instancing‌,MPB是实现高性能差异化渲染的核心.

using UnityEngine;

public class BulkColorChanger : MonoBehaviour
{
    // 缓存 MPB 对象,避免每帧 new 造成 GC
    private MaterialPropertyBlock mpb;
    private Renderer[] renderers;
    
    // 假设这是你要设置的目标颜色数组,或者通过逻辑计算得出
    public Color[] targetColors; 

    void Awake()
    {
        mpb = new MaterialPropertyBlock();
        // 获取所有需要修改颜色的 Renderer
        renderers = GetComponentsInChildren<Renderer>();
    }

    void Update()
    {
        // 模拟每帧或定期更新颜色
        for (int i = 0; i < renderers.Length; i++)
        {
            if (renderers[i] == null) continue;

            // 1. 获取当前的MPB状态(可选,如果完全覆盖可跳过)
            renderers[i].GetPropertyBlock(mpb);
            
            // 2. 设置新的颜色属性
            // 注意:Shader 中的属性名必须匹配,通常是 "_Color" 或 "_BaseColor"
            mpb.SetColor("_Color", targetColors[i % targetColors.Length]);
            
            // 3. 应用回 Renderer
            renderers[i].SetPropertyBlock(mpb);
        }
    }
}

3. 进阶优化:GPU Instancing (必开)

对于 20,000 个物体,仅靠 MPB 在传统管线中可能仍受限于动态合批的顶点数限制(通常 <900 顶点).必须启用 ‌GPU Instancing‌.

操作步骤
材质设置‌:选中那个唯一的共享材质,在 Inspector 面板勾选 ‌Enable GPU Instancing‌.
Shader 支持‌:
如果使用 Unity 标准 Shader 或 URP Lit/Unlit,默认已支持.
如果使用自定义 Shader,需确保添加了 #pragma multi_compile_instancing 并在 CG/HLSL 代码中使用 UNITY_INSTANCING_BUFFER 宏来声明每实例数据(如颜色).
效果‌:
Unity 会将这 20,000 个精灵的变换矩阵和 MPB 中的颜色数据打包,通过 ‌1 次或极少几次 Draw Call‌ 发送给 GPU.GPU 并行处理每个实例的颜色差异.

排序层(Sorting Layer)‌:MPB 不影响排序,但大量 Sprite 需要注意 Sorting Order 的管理,以免遮挡关系错误.

使用单个共享材质 + MaterialPropertyBlock + GPU Instancing‌ 的组合.这将使你的渲染性能提升数个数量级,从不可用变为流畅运行.
针对 20,000 个精灵(Sprite)频繁修改颜色的场景,使用 MaterialPropertyBlock (MPB) 是最佳实践.
以下是经过优化的具体代码示例,涵盖了‌基础用法‌、‌高性能优化写法‌以及‌Shader 配置要求‌.

1. 核心代码示例:批量设置颜色

这段代码展示了如何高效地为大量 Renderer 设置不同的颜色,同时避免 GC(垃圾回收)和重复查找属性 ID.

using UnityEngine;

public class SpriteColorManager : MonoBehaviour
{
    [Header("配置")]
    public SpriteRenderer[] spriteRenderers; // 在 Inspector 中赋值或通过代码获取
    
    // 缓存 MaterialPropertyBlock,避免每帧 new 对象产生 GC
    private MaterialPropertyBlock mpb;
    
    // 缓存 Shader 属性 ID,避免每帧通过字符串查找属性,提升性能
    private int colorPropertyId;

    void Awake()
    {
        // 1. 初始化 MPB
        mpb = new MaterialPropertyBlock();
        
        // 2. 获取颜色属性的 ID (假设 Shader 中颜色变量名为 "_Color")
        // 如果是 URP Lit/Unlit,可能是 "_BaseColor",请根据实际 Shader 调整
        colorPropertyId = Shader.PropertyToID("_Color");
        
        // 3. 确保所有 SpriteRenderer 使用的材质开启了 GPU Instancing
        // 注意:这里只读取 sharedMaterial 进行检查,不修改它
        if (spriteRenderers.Length > 0 && spriteRenderers != null)
        {
            Material mat = spriteRenderers.sharedMaterial;
            if (mat != null && !mat.enableInstancing)
            {
                Debug.LogWarning("材质未开启 GPU Instancing,可能导致 Draw Call 无法合并！请在材质面板勾选 'Enable GPU Instancing'.");
            }
        }
    }

    void Update()
    {
        // 模拟每帧更新颜色(例如根据时间或游戏逻辑变化)
        for (int i = 0; i < spriteRenderers.Length; i++)
        {
            if (spriteRenderers[i] == null) continue;

            // --- 关键步骤 A: 获取当前的 PropertyBlock ---
            // 如果之前已经设置过 MPB,这一步会复制之前的状态到 mpb 变量中.
            // 如果这是第一次设置,mpb 将是空的.
            // 这样做是为了防止覆盖该 Renderer 上可能存在的其他属性(如透明度、贴图偏移等).
            spriteRenderers[i].GetPropertyBlock(mpb);

            // --- 关键步骤 B: 设置新的颜色值 ---
            // 使用缓存的 ID 比使用字符串 "_Color" 更快
            Color newColor = GetDynamicColor(i); 
            mpb.SetColor(colorPropertyId, newColor);

            // --- 关键步骤 C: 应用回 Renderer ---
            spriteRenderers[i].SetPropertyBlock(mpb);
        }
    }

    // 示例:生成动态颜色
    private Color GetDynamicColor(int index)
    {
        // 这里替换为你真实的颜色计算逻辑
        float hue = (index * 0.1f + Time.time * 0.1f) % 1.0f;
        return Color.HSVToRGB(hue, 1.0f, 1.0f);
    }
}

2. 为什么这样写性能最高？

缓存 MaterialPropertyBlock 实例‌:

错误做法‌:在 Update 循环中 new MaterialPropertyBlock().这会导致每帧产生 20,000 次内存分配,引发严重的 GC卡顿.
正确做法‌:在 Awake 或 Start 中创建一次,后续复用同一个对象.MPB 是轻量级结构,复用非常安全.

缓存 Shader.PropertyToID‌:

错误做法‌:mpb.SetColor("_Color", color).每次调用都需要在Shader属性表中通过字符串哈希查找ID,开销较大.
正确做法‌:mpb.SetColor(id, color).直接使用整数ID,速度极快.

先 GetPropertyBlock 再 SetPropertyBlock‌:
MPB 是“覆盖”机制.如果你直接 SetColor 然后 SetPropertyBlock,它会‌清除‌该 Renderer 上之前设置的其他所有 MPB 属性(比如你之前设置的 _Alpha 或 _Offset).
先 Get 可以把现有的覆盖数据读入 mpb 对象,然后再修改其中的颜色,最后 Set 回去,保证其他属性不被意外重置.

3. Shader 与材质配置要求(至关重要)
为了让 MPB 发挥最大效能(即保持合批),你必须确保 Shader 和材质支持 ‌GPU Instancing‌.

A. 材质设置
选中项目中被这 20,000 个精灵共享的那个 ‌Material‌.
在 Inspector 面板底部,勾选 ‌Enable GPU Instancing‌.
如果不勾选:虽然 MPB 不会创建材质实例,但每个 Sprite 可能仍然无法合批,导致 Draw Call 飙升.
如果勾选:Unity 会将具有相同 Mesh 和 Material 但不同 MPB 数据的物体合并到一个 Draw Call 中(通过 Instance ID 区分).

B. Shader代码支持(如果是自定义 Shader)
如果你使用的是 Unity 内置的 Sprites-Default 或 URP 的 Sprite-Lit-Default,它们通常已经支持 Instancing.如果是自定义 Shader,需要添加以下宏:
Shader "Custom/InstancedColorSprite"
{
    Properties
    {
        _MainTex ("Texture", 2D) = "white" {}
        _Color ("Color", Color) = (1,1,1,1)
    }
    SubShader
    {
        Tags { "RenderType"="Transparent" "Queue"="Transparent" }
        
        Pass
        {
            CGPROGRAM
            #pragma vertex vert
            #pragma fragment frag
            #pragma multi_compile_instancing  // <--- 关键:启用 instancing 变体
            
            #include "UnityCG.cginc"

            struct appdata
            {
                float4 vertex : POSITION;
                float2 uv : TEXCOORD0;
                UNITY_VERTEX_INPUT_INSTANCE_ID // <--- 关键:声明实例 ID
            };

            struct v2f
            {
                float2 uv : TEXCOORD0;
                float4 vertex : SV_POSITION;
            };

            sampler2D _MainTex;
            float4 _MainTex_ST;
            
            // 定义实例化缓冲区中的颜色属性
            UNITY_INSTANCING_BUFFER_START(Props)
                UNITY_DEFINE_INSTANCED_PROP(fixed4, _Color) // <--- 关键:将颜色定义为实例化属性
            UNITY_INSTANCING_BUFFER_END(Props)

            v2f vert (appdata v)
            {
                v2f o;
                UNITY_SETUP_INSTANCE_ID(v); // <--- 关键:设置实例 ID
                
                o.vertex = UnityObjectToClipPos(v.vertex);
                o.uv = TRANSFORM_TEX(v.uv, _MainTex);
                return o;
            }

            fixed4 frag (v2f i) : SV_Target
            {
                // 获取当前实例的颜色
                fixed4 col = UNITY_ACCESS_INSTANCED_PROP(Props, _Color);
                fixed4 tex = tex2D(_MainTex, i.uv);
                return tex * col;
            }
            ENDCG
        }
    }
}

通过上述代码和配置,你可以轻松处理 20,000+ 精灵的颜色动态变化,同时保持极低的 CPU 开销和 Draw Call 数量.

URP管线在构建打包时,默认会根据项目中‌已使用材质的LightMode标签组合‌自动剔除未被引用的Shader变体,从SO文件读取的自定义Shader其GPU实例化相关的编译变体很容易被误删
编辑器中资源校验宽松,修改顶点颜色不会打断实例化,但打包后严格执行GPU实例化合批规则,会导致打包前后改色等效果不一致.
若打包前有精灵白闪效果,打包后丢失GPU实例化的该效果,那么去编辑器菜单-项目设置-图形-找到"实例化变体"选择"保持全部"即可解决.

手动锁定Shader变体防止被Strip‌
项目中新建一个ShaderVariantCollection资源,把你自定义Shader的「Universal2D+带GPU实例化」「NormalsRendering+带GPU实例化」「UniversalForward+带GPU实例化」所有变体键值全部手动添加进去,
在Unity的Project Settings > Graphics > Shader Stripping面板,指定使用这个变体集合,强制打包时保留所有需要的GPU实例化相关变体.
提前将自定义Shader放入非Resources目录,再把它配置进Project Settings > Graphics的Always Included Shaders列表里,保证打包时Shader不会被误删,SO文件从资源路径加载Shader即可正常获取到有效Shader资源.

即使 SO 文件在 Resources 目录下且引用了 Shader,打包后依然可能出现受击无反应的情况,原因及正确做法如下:

1. 为什么“SO在Resources里”还不够？

Unity 的打包机制分为‌资源引用追踪‌和‌Shader变体编译‌两个独立阶段:
资源引用阶段‌:SO 在 Resources 下,确实能保证 SO 资产本身以及它直接引用的 Shader ‌源代码文件‌被打入包体.这意味着运行时 Load 能拿到 Shader 对象,不会报“Missing Shader”粉色错误.
变体编译阶段‌:Unity 在构建时会分析项目中所有‌已使用材质(Material)‌的关键字组合,来决定编译哪些 Shader 变体.
原因:凡运行时动态新建材质‌并赋值Shader的情况,在打包构建时,这些动态生成的材质并不存在,Unity的静态分析器无法预知会用到哪些关键字组合,从而默认剥离未使用的变体(特别是 INSTANCING_ON 这种 GPU 实例化关键字).
虽然Shader代码在包里,但‌包含 GPU 实例化逻辑的具体变体代码可能被剔除(Strip)了‌.

3. 正确使用 Shader Variant Collection (SVC)

既然动态创建材质,必须手动告诉 Unity 哪些变体是必需的.请按照以下步骤操作:

步骤一:创建变体集合
在 Project 窗口右键 -> Create -> Shader -> Shader Variant Collection.
命名为 FlashShaderVariants.

步骤二:收集必要变体
手动添加(推荐用于少量明确变体)‌:
打开 SVC 文件,点击 + 号添加你的自定义 Shader.
展开 Shader,你会看到不同的 Pass(如 Universal2D, UniversalForward).
对于每个 Pass,确保添加了包含 INSTANCING_ON 关键字的变体.
技巧:如果不确定具体关键字,可以在编辑器中运行游戏,触发一次白闪效果,然后选中 SVC 文件,在 Inspector 中点击 Collect Current(如果支持)或使用第三方工具收集当前运行时用到的变体.
确保覆盖所有 Pass‌:
假设Shader有三个Pass(Universal2D, NormalsRendering, UniversalForward).
确保 SVC 中包含了这三个 Pass 在‌开启 GPU 实例化‌状态下的变体.

步骤三:确保 SVC 被打包
如果使用 Resources‌:将 .shadervariants 文件放入 Resources 文件夹.
如果使用 Addressables/AssetBundles‌:确保该 SVC 文件被标记为可寻址或打入 Bundle,并在游戏启动早期加载.

步骤四:预热(可选但推荐)
在游戏启动或场景加载时,调用 SVC 的预热方法,避免首次触发白闪时的即时编译卡顿:
public ShaderVariantCollection flashVariants; // 在Inspector赋值或加载
void Start() {
    if (flashVariants != null) {
        flashVariants.WarmUp();
    }
}

4. 额外检查:Strict Shader Variant Matching
在 Project Settings > Player 中,有一个选项叫 ‌Strict Shader Variant Matching‌(严格着色器变体匹配):

建议开启‌:在测试阶段开启此选项.如果打包后缺少变体,Unity 会在控制台打印明确的错误日志,告诉你具体缺了哪个 Pass 和哪些关键字,而不是 silently fail(静默失败,即没效果也不报错).
注意‌:开启后,如果变体缺失,Shader 会变成粉色或黑色.这有助于你精准定位 SVC 中漏掉了哪个变体.
